# Architectural Decision Records (ADR)

## 1. Выбор блокчейна: TON (The Open Network)

**Статус:** Принято

**Контекст:**
Требуется блокчейн-платформа для проведения лаунчей с высокой пропускной способностью, низкими комиссиями и интеграцией с Telegram.

**Варианты:**

- **Ethereum**: Наибольшая экосистема DeFi, но высокие gas fees ($5-50 за транзакцию) и медленное время блока (12 сек).
- **Solana**: Высокая скорость (400мс), но сложная интеграция с Telegram и частые сбои сети.
- **TON**: Нативная интеграция с Telegram, низкие комиссии ($0.01-0.05), высокая TPS (до 100k).

**Выбор:** TON (The Open Network)

**Обоснование:**

- Нативная интеграция с Telegram через Mini Apps и TON Connect обеспечивает доступ к 900M+ пользователей.
- Sharding-архитектура позволяет масштабироваться без увеличения комиссий.
- Язык FunC/Tact для смарт-контрактов оптимизирован под асинхронные вызовы.

**Последствия:**

- (+) Комиссии в 100-500 раз ниже, чем в Ethereum.
- (+) Время финализации транзакции ~5 секунд.
- (-) Меньше разработчиков и инструментов по сравнению с EVM-экосистемой.
- (-) Специфичный язык FunC требует дополнительного обучения команды.

## 2. Backend Framework: Elysia.js

**Статус:** Принято

**Контекст:**
Требуется высокопроизводительный HTTP-сервер для API с поддержкой TypeScript и валидацией схем.

**Варианты:**

- **Express.js**: Зрелая экосистема, но низкая производительность (15k req/s) и отсутствие встроенной типизации.
- **Fastify**: Высокая скорость (75k req/s), но сложная интеграция с TypeBox.
- **Elysia.js**: Максимальная производительность (90k req/s на Bun), end-to-end типизация, встроенная валидация.

**Выбор:** Elysia.js + Bun runtime

**Обоснование:**

- Производительность в 6 раз выше Express благодаря Bun runtime.
- End-to-end типизация от схемы запроса до ответа без генерации кода.
- Встроенная поддержка Swagger/OpenAPI документации.

**Последствия:**

- (+) Сокращение boilerplate-кода на 40% по сравнению с Express.
- (+) Автоматическая генерация типов для клиента.
- (-) Bun менее стабилен, чем Node.js для production (смягчается через Docker-изоляцию).

## 3. Frontend: Telegram Mini App (TMA)

**Статус:** Принято

**Контекст:**
Требуется пользовательский интерфейс с максимальным охватом аудитории и простотой onboarding.

**Варианты:**

- **Standalone Web App**: Полный контроль над UX, но требует отдельной регистрации пользователей.
- **Native Mobile App**: Лучший UX, но долгая модерация в App Store/Google Play и высокая стоимость разработки.
- **Telegram Mini App**: Мгновенный доступ через Telegram, встроенная авторизация, viral-распространение.

**Выбор:** Telegram Mini App (Next.js)

**Обоснование:**

- Zero-friction onboarding: пользователь уже авторизован через Telegram.
- Встроенные платежи через TON Connect без перехода в внешние кошельки.
- Viral-механики: share-кнопки для распространения лаунчей в чатах.

**Последствия:**

- (+) CAC (Customer Acquisition Cost) снижен на 80% за счёт organic-трафика.
- (+) Нет необходимости в App Store оптимизации.
- (-) Ограничения платформы Telegram (размер бандла, отсутствие push-notifications вне чата).

## 4. База данных: PostgreSQL

**Статус:** Принято

**Контекст:**
Требуется СУБД для хранения данных о пользователях, лаунчах, транзакциях с поддержкой сложных запросов.

**Варианты:**

- **MongoDB**: Гибкая схема, но отсутствие ACID для финансовых операций.
- **MySQL**: Широко распространена, но слабая поддержка JSON и массивов.
- **PostgreSQL**: Полный ACID, богатые типы данных (JSONB, arrays), расширяемость.

**Выбор:** PostgreSQL + postgres.js

**Обоснование:**

- ACID-гарантии критичны для финансовых операций (балансы, транзакции).
- JSONB позволяет хранить метаданные токенов без миграций схемы.
- postgres.js обеспечивает type-safe запросы через tagged templates с минимальным overhead.

**Последствия:**

- (+) Возможность сложных аналитических запросов через window functions.
- (+) Встроенная поддержка full-text search для поиска лаунчей.
- (-) Требует настройки репликации для high availability (решается через managed PostgreSQL).

## 5. Хранение метаданных: IPFS

**Статус:** Принято

**Контекст:**
Требуется децентрализованное хранилище для метаданных токенов (изображения, описания), которые ссылаются из смарт-контрактов.

**Варианты:**

- **Centralized CDN (S3)**: Быстро и дёшево, но single point of failure и цензуроопасность.
- **Arweave**: Permanent storage, но высокая стоимость ($5+ за МБ).
- **IPFS**: Децентрализованное хранение, content-addressing, бесплатное при self-hosting.

**Выбор:** Self-hosted IPFS Node

**Обоснование:**

- Content-addressing гарантирует, что метаданные не могут быть подменены после публикации.
- Стандарт для NFT/токенов: кошельки и маркетплейсы автоматически резолвят IPFS-ссылки.
- Self-hosted нода обеспечивает контроль над доступностью данных.

**Последствия:**

- (+) Метаданные сохраняются навсегда при наличии хотя бы одной пинящей ноды.
- (+) Интероперабельность с другими Web3-сервисами.
- (-) Требует мониторинга IPFS-ноды и периодического garbage collection.

## Итоговая архитектура

Архитектурные решения оптимизированы под следующие приоритеты:

1. **Низкий барьер входа** — Telegram Mini App + TON Connect обеспечивают мгновенный onboarding.
2. **Производительность** — Elysia.js + Bun + PostgreSQL обеспечивают low-latency API.
3. **Децентрализация** — TON blockchain + IPFS гарантируют censorship-resistance.
4. **Масштабируемость** — Microservices архитектура (Oracle, Manager, Dispenser) позволяет независимое масштабирование.
5. **AI-интеграция** — LLM-чатбот с RAG обеспечивает умную поддержку пользователей.
